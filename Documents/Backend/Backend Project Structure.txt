# 🏗️ MediMind — Backend Project Structure

Now we define the **actual folder structure** for the backend. This will make implementation much easier because every microservice follows the same pattern.

---

# 3. Why `controllers` and `services` are Separate

We'll follow:

```text
Route
  ↓
Controller
  ↓
Service
  ↓
Model
  ↓
Database
```

For example:

```text
POST /api/families/members
          ↓
family.routes.js
          ↓
familyMemberController.js
          ↓
familyMemberService.js
          ↓
FamilyMember Model
          ↓
MongoDB
```

This keeps business logic out of the route files.

# 11. Medical Record Service 🗂️

This service manages medical records, consultations, prescriptions, and doctor access authorization.

The access feature is **not a separate microservice**. It is part of the Medical Record Service and is represented by the `RecordAccess` model.

```text
medical-record-service/
│
├── controllers/
│   ├── medicalRecordController.js
│   ├── consultationController.js
│   ├── prescriptionController.js
│   └── recordAccessController.js
│
├── models/
│   ├── MedicalRecord.js
│   ├── Consultation.js
│   ├── Prescription.js
│   └── RecordAccess.js
│
├── routes/
│   ├── medicalRecordRoutes.js
│   ├── consultationRoutes.js
│   ├── prescriptionRoutes.js
│   └── recordAccessRoutes.js
│
└── services/
    ├── medicalRecordService.js
    ├── consultationService.js
    ├── prescriptionService.js
    └── recordAccessService.js
```

`RecordAccess` stores which doctor is authorized for which family member. Access is all-or-nothing for the selected member; there are no granular record-type permissions.

# 14. Environment Variables

Each service gets its own `.env`.

### Example Node service

```env
PORT=5002
MONGO_URI=mongodb+srv://...
JWT_SECRET=...
```

But we should **not put the same database URI in every service**.

For example:

```text
Family Service
      ↓
medimind_family


Doctor Service
      ↓
medimind_doctor
```

The MongoDB deployment can be the same, but the logical databases differ.

# 16. One Important Implementation Decision

We'll **not create a huge shared backend package** such as:

```text
shared-models/
shared-database/
shared-services/
```

because that can blur service ownership.

Instead, each service owns its:

```text
models
controllers
services
routes
database connection
```

The only things that can be standardized are lightweight concepts such as:

```text
JWT format
API response format
HTTP status conventions
environment variable naming
```
