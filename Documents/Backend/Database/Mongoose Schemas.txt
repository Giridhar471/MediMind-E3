# 1. 🔐 Auth Service

## `User.js`

```js
import mongoose from "mongoose";

const userSchema = new mongoose.Schema(
  {
    email: {
      type: String,
      required: true,
      unique: true,
      lowercase: true,
      trim: true,
      index: true
    },

    password_hash: {
      type: String,
      required: true
    },

    role: {
      type: String,
      required: true,
      enum: [
        "FAMILY",
        "DOCTOR",
        "DEPARTMENT_HEAD",
        "HOSPITAL_ADMIN",
        "CHAIRMAN"
      ]
    },

    account_type: {
      type: String,
      required: true,
      enum: [
        "FAMILY_ACCOUNT",
        "DOCTOR_ACCOUNT",
        "DEPARTMENT_HEAD_ACCOUNT",
        "HOSPITAL_ADMIN_ACCOUNT",
        "CHAIRMAN_ACCOUNT"
      ]
    },

    reference_id: {
      type: mongoose.Schema.Types.ObjectId,
      required: true
    },

    status: {
      type: String,
      enum: ["ACTIVE", "INACTIVE", "DELETED"],
      default: "ACTIVE"
    },

    last_login_at: {
      type: Date,
      default: null
    }
  },
  {
    timestamps: {
      createdAt: "created_at",
      updatedAt: "updated_at"
    }
  }
);

const User = mongoose.model("User", userSchema);

export default User;
```

However, because we want prediction history in MongoDB, we'll maintain an equivalent MongoDB document structure.

# 11. 🔗 Relationships Between Services

Because these are **microservices**, these IDs are references, but **not Mongoose `populate()` references across databases**.

For example:

```text id="2b6c81"
Appointment Service
      │
      ├── family_member_id
      ├── doctor_id
      ├── hospital_id
      ├── department_id
      └── ai_prediction_id
```

Those IDs point conceptually to entities owned by other services.

The service communicates through REST when it needs additional information.

Those aren't part of our current core implementation.

# 15. One Small Architecture Detail to Keep in Mind

There is one important distinction between **the database blueprint** and **the final implementation schema**.

The structures above are our **locked design baseline**.

When we actually implement each service, we can add technical details such as:

* compound indexes
* custom validators
* unique constraints
* middleware/hooks where genuinely useful
* file validation
* pagination indexes
* query optimization

without changing the overall business model.
