# 🗄️ MediMind — Full Database Structure

Yes. Now that **Roles 1–5, permissions, doctor authorization, AI workflow, and the removal of Notifications** are finalized, we can lock the complete database structure.

We'll use **MongoDB + Mongoose**, with **database-per-service** using one MongoDB Atlas deployment.

---

# 1. 🏗️ Final Database Architecture

```text
                         MongoDB Atlas
                              │
       ┌──────────────────────┼──────────────────────┐
       ↓                      ↓                      ↓
 medimind_auth          medimind_family       medimind_hospital
       │                      │                      │
     users                 families              hospitals
                            members              departments
                                                   dept_heads
       │
       ├───────────────┐
       ↓               ↓
medimind_doctor   medimind_appointment
       │               │
    doctors        appointments
       │               │
       └───────┬───────┘
               ↓
       medimind_records
               │
       ┌───────┼──────────┐
       ↓       ↓          ↓
    records  consultations prescriptions
               │
               ↓
         record_access


       medimind_ai
             │
        predictions


       medimind_knowledge
             │
          articles
```

### Final services

| # | Service                    | Database               |
| - | -------------------------- | ---------------------- |
| 1 | 🚪 API Gateway             | —                      |
| 2 | 🔐 Auth Service            | `medimind_auth`        |
| 3 | 👨‍👩‍👧 Family Service    | `medimind_family`      |
| 4 | 🏥 Hospital Service        | `medimind_hospital`    |
| 5 | 👨‍⚕️ Doctor Service       | `medimind_doctor`      |
| 6 | 📅 Appointment Service     | `medimind_appointment` |
| 7 | 🗂️ Medical Record Service | `medimind_records`     |
| 8 | 🤖 AI Prediction Service   | `medimind_ai`          |
| 9 | 📚 Knowledge Service       | `medimind_knowledge`   |

**Notification Service is removed for now.**

# 2. 🔐 `medimind_auth`

This database manages **authentication and login identity**.

```text
medimind_auth
└── users
```

## `users`

```js
{
  _id: ObjectId,

  email: String,
  password_hash: String,

  role: String,

  account_type: String,

  reference_id: ObjectId,

  status: String,

  last_login_at: Date,

  created_at: Date,
  updated_at: Date
}
```

### `role`

```text
FAMILY
DOCTOR
DEPARTMENT_HEAD
HOSPITAL_ADMIN
CHAIRMAN
```

### `account_type`

```text
FAMILY_ACCOUNT
DOCTOR_ACCOUNT
DEPARTMENT_HEAD_ACCOUNT
HOSPITAL_ADMIN_ACCOUNT
CHAIRMAN_ACCOUNT
```

### `status`

```text
ACTIVE
INACTIVE
DELETED
```

---

## Important relationship

For a family:

```text
users
   │
   └── reference_id
            ↓
         family_id
```

For a doctor:

```text
users
   │
   └── reference_id
            ↓
         doctor_id
```

Therefore, the authentication service doesn't need to store the entire doctor/family profile.

```text

              ↓
```


The AI prediction can therefore be directly associated with the appointment.

# 32. ⭐ Doctor Access Logic

Suppose:

```text
Family F001

├── Father M001
├── Mother M002
└── Son M003
```

Family grants:

```text
M002 → Doctor D001
```

Database:

```text
record_access

{
    family_member_id: M002,
    doctor_id: D001,
    status: "ACTIVE"
}
```

Then:

```text
D001 → M002 → ALL authorized records
```

But:

```text
D001 → M001 ❌
D001 → M003 ❌
```

unless separately authorized.

# 37. 🌐 Public Knowledge

Once published:

```text
PUBLISHED ARTICLE
       │
       ├── Doctors ✅
       ├── Medical Staff ✅
       ├── Family Users ✅
       └── Public Users ✅
```

But:

```text
Private Patient Data
        ↓
Public Article ❌
```

Patient information must not be exposed through knowledge articles without appropriate authorization/anonymization.

# 41. 👨‍👩‍👧 Family → Doctor Relationship

This is **not** stored directly inside `families`.

Instead:

```text
family_members
      │
      ↓

      │
      ↓
doctors
```

Example:

```text
Mother M002
      ↓
record_access
      ↓
Doctor D004
```

This means:

> Doctor D004 is authorized to access Mother M002.
