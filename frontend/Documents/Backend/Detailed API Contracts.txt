# 🔌 MediMind — Detailed API Contracts

Now we move from the **architecture level** to the **actual API contract level**.

We don't need to implement anything yet. We'll first lock what each endpoint accepts, who can call it, and what it returns.

---

# 1. API Contract Convention

All APIs will follow:

```text
/api/<resource>
```

Responses will use JSON.

### Success

```json
{
  "success": true,
  "message": "Operation successful",
  "data": {}
}
```

### Error

```json
{
  "success": false,
  "message": "Something went wrong"
}
```

For validation errors:

```json
{
  "success": false,
  "message": "Validation failed",
  "errors": {}
}
```

# 2. Authentication APIs 🔐

## `POST /api/auth/login`

### Allowed

```text
FAMILY
DOCTOR
DEPARTMENT_HEAD
HOSPITAL_ADMIN
CHAIRMAN
```

### Request

```json
{
  "email": "user@example.com",
  "password": "password123"
}
```

### Response

```json
{
  "success": true,
  "message": "Login successful",
  "data": {
    "token": "JWT_TOKEN",
    "user": {
      "userId": "...",
      "role": "FAMILY",
      "referenceId": "..."
    }
  }
}
```

---

## `POST /api/auth/logout`

Requires JWT. The client clears its authentication state/token after logout.

---

## `GET /api/auth/me`

Requires JWT.

Returns the currently authenticated user.

```json
{
  "success": true,
  "data": {
    "userId": "...",
    "role": "DOCTOR",
    "referenceId": "..."
  }
}
```

---

## `POST /api/auth/change-password`

Requires JWT.

```json
{
  "currentPassword": "oldPassword",
  "newPassword": "newPassword"
}
```

# 8. Appointment + AI

Every appointment requires an AI prediction.

The appointment stores the linked prediction ID:

```json
{
  "aiPredictionId": "67abc..."
}
```

The prediction is created as part of the appointment workflow and linked through `aiPredictionId`.

So:

```text
Appointment
     │
     └──── AI Prediction
```


Returns the unified medical records of that patient.

---

## Get Record

```http
GET /api/records/:recordId
```


## Doctor Access — Grant Access

```http
POST /api/records/access
```

A family account can grant a doctor full medical-record access for a specific family member.

Request:

```json
{
  "familyMemberId": "...",
  "doctorId": "..."
}
```

Access is all-or-nothing for the selected family member. There are no individual record-type permission checkboxes.

---

## Doctor Access — Current Access

```http
GET /api/records/access/member/:memberId
```

Returns the active doctors authorized for the selected family member.

---

## Doctor Access — Revoke Access

```http
PUT /api/records/access/:accessId/revoke
```

Only the family account can revoke access it previously granted.

---

## Doctor Access — Doctor History

```http
GET /api/records/access/doctor/me
```

Returns the authenticated doctor's access history.

# 20. Important Service-to-Service Calls

We don't want random communication between every service.

The main flows are:

### Appointment → Doctor

```text
Appointment Service
       ↓
Doctor Service
       ↓
Check doctor/availability
```

### Appointment → AI

```text
Appointment Service
       ↓
AI Prediction Service
       ↓
Create required prediction
```

### Doctor/Family → Records

```text
Doctor/Family
      ↓
API Gateway
      ↓
Medical Record Service
```

### Knowledge → Doctor/Department

```text
Knowledge Service
       ↓
Doctor identity
Department identity
```

using IDs and authenticated context.

# 21. Unified Healthcare Workflow

This is the **core business flow** of MediMind:

```text
┌──────────────────┐
│   FAMILY LOGIN   │
└────────┬─────────┘
         ↓
┌──────────────────┐
│ SELECT PATIENT   │
└────────┬─────────┘
         ↓
 ┌───────┼──────────┐
 ↓       ↓          ↓
Records AI       Appointment
         │          │
         │          ▼
         │       Required AI
         │          │
         └────┬─────┘
              ↓
           Doctor
              ↓
        Medical History
              +
        AI Prediction
              ↓
         Consultation
              ↓
         Prescription
```

This is the workflow that ties the **SOA + PDNC + ASE** parts together.

# 22. Error Handling

We'll standardize HTTP status codes.

| Code  | Meaning               |
| ----- | --------------------- |
| `200` | Successful request    |
| `201` | Resource created      |
| `400` | Bad request           |
| `401` | Not authenticated     |
| `403` | Not authorized        |
| `404` | Resource not found    |
| `409` | Conflict              |
| `422` | Validation error      |
| `500` | Internal server error |
| `503` | Service unavailable   |

Example:

```json
{
  "success": false,
  "message": "Doctor is not available at the selected time"
}
```

with:

```http
409 Conflict
```

# 23. What We Have Locked

At this point the backend architecture is:

```text
                    React
                      ↓
                API Gateway
                      ↓
 ┌─────────┬─────────┼─────────┬─────────┬───────────┐
 ↓         ↓         ↓         ↓         ↓
Auth     Family   Hospital   Doctor   Appointment
                                           ↓
                                           AI
                                           
                    ↓
              Medical Records
                    ↓
          ┌─────────┴─────────┐
          ↓                   ↓
   Consultations         Prescriptions

                    +

              Knowledge Service
```

### And importantly:

* ✅ Doctor Access is represented by `record_access` within the Medical Record Service; there is no separate standalone access service
* ❌ No notification service
* ❌ No granular record-type permissions
* ❌ No direct database sharing
* ❌ No GraphQL
* ❌ No Redis/RabbitMQ/Kafka
* ✅ REST APIs
* ✅ API Gateway
* ✅ JWT
* ✅ Role-based authorization
* ✅ Database-per-service
* ✅ Four AI modules
* ✅ Independent AI predictions
* ✅ AI prediction required for every appointment
* ✅ Unified medical records
* ✅ Consultation → Prescription
* ✅ Doctor article → Department Head review → Publish
